Facts that contradict common assumptions — the CODE is authoritative:
- There is **no `has_blocking_issues` top-level field**. Derive it yourself:
  `items.some(i => i.issues.length > 0)`. Per-item issue codes are `price_changed`,
  `insufficient_stock`, `product_unavailable` (see `revalidate_cart` in `api/orders/services.py`).
- **`total` always equals `subtotal`.** There is no delivery fee, tax or discount anywhere in the
  backend. Remove the hardcoded `deliveryFeeNum = 15.0`.
- An empty cart returns `items: []`, `seller: null`, `subtotal`/`total` `"0.00"`.
- **`DELETE /cart/items/<id>/` returns 204 with NO body** — you must re-fetch `GET /cart/` after a
  delete. `POST /cart/items/` returns 201 *with* the cart body; `PATCH /cart/items/<id>/` returns 200
  *with* the cart body. `DELETE /cart/` returns 204.
- `PATCH /cart/items/<id>/` also resets the stored price to the current price, so a `price_changed`
  issue on that line clears as a side effect of a quantity update.
- All cart endpoints require `IsCustomer` — a seller or admin account gets a 403.

Error codes to surface as readable UI, never as a crash (from `api/orders/views.py`):
- `multi_seller_cart` (**409**) on `POST /cart/items/` when the cart already holds another seller's
  product. `details.current_seller = {id, business_name}`. The existing conflict dialog in the cart
  UI should render this with the real seller name, offering "clear cart and add this instead"
  (`DELETE /cart/` then retry the add) or "keep current cart".
- `insufficient_stock` (**400** on cart add/update) with `details.available` — note `available` is
  **omitted** when stock is above the low-stock threshold, so treat it as optional.
- `product_not_purchasable` (400) — product missing, unpublished, or seller inactive.
- `invalid_quantity` (400).

**Guest cart.** A logged-out visitor has no server cart (the endpoints are auth-only). Keep the

item by item via `POST /cart/items/`. The replay must handle real failures rather than silently losing
items:
- `multi_seller_cart` → the server cart wins by default; collect the dropped lines and report them.
- `insufficient_stock` / `product_not_purchasable` → skip that line, collect it.

## 2. Checkout — `app/[locale]/checkout/page.tsx`

`POST /checkout/` with body `{contact_name, contact_phone, delivery_address, price_acknowledgements}`
and header `Idempotency-Key`. Read `CheckoutView` in `api/orders/views.py` and `CheckoutSerializer` in
`api/orders/serializers.py`.
- The **`Idempotency-Key` must be a valid UUID** (`uuid.UUID(...)` is parsed server-side; a non-UUID
  gets `missing_idempotency_key` 400). Generate it with `crypto.randomUUID()` **once per checkout
  attempt**, hold it in a ref, and reuse the same key across retries of that attempt. Disable the
  confirm button while the request is in flight.
- **201** = order created. **200** = this exact key already created an order and the backend replayed
  it — treat both identically and go to the confirmation screen. Both return
  `CustomerOrderDetailSerializer`.
- The price-acknowledgement key is **`price_acknowledgements`**, an array of `{product_id, new_price}`.
  `API.md` calls it `acknowledged_issues` — **the doc is wrong, the code wins.** Do not "fix" it to
  match the doc. The acknowledged `new_price` must equal the server's current price exactly or
  checkout fails again.
- **409 `cart_has_issues`**: `details` is a **single issue object**, NOT an array —
  `{"issue": "price_changed", "product_id": 5, "old_price": "28.00", "new_price": "30.00"}` or
  `{"issue": "product_unavailable", "product_id": 5}`. Only `price_changed` is acknowledgeable: show
  the old→new price and an "accept new price" action that retries checkout with that product in
  `price_acknowledgements`. `product_unavailable` must be resolved by editing the cart.
- **409 `insufficient_stock`** at checkout (note: 409 here, 400 on the cart endpoints) with
  `details.product_id` and optional `details.available` — send the user back to the cart to fix it.
- 400 `empty_cart`.
